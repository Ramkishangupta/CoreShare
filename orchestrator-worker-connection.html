Orchestrator-Worker I/O Connection Analysis

1. Connection Architecture Overview

The system uses a Client-Server architecture where the Orchestrator acts as the WebSocket Server and each Worker acts as a Client. The communication is persistent, real-time, and bi-directional, enabled by the Socket.IO library.

2. Use of Socket Protocol & Logic

The connection relies on the WebSocket protocol, wrapped by Socket.IO for reliability (auto-reconnection, packet buffering). This ensures that if a network glitch occurs, the worker automatically attempts to reconnect (`MaxReconnectAttempts: 10`).

Key Protocol Features in this System:

  • Authentication: Connection handshake includes an auth object with a secret token (WORKER_SECRET_TOKEN).
  • Event-Driven: Communication is message-based, not request-response. Events like job:new or job:status can be sent at any time.
  • Heartbeat Mechanism: Application-level ping to track worker health/load (every 30s).
  • Namespaces: All workers connect to the default root namespace /.

3. Complete Connection Flow

Phase 1: Connection & Registration

When a worker starts, it initiates a connection. Once connected, it must "register" to identify its capabilities (CPU/GPU specs).

            sequenceDiagram
                participant W as Worker Client
                participant O as Orchestrator Server
                participant DB as Database

                Note over W: Worker Starts
                W->>O: Connect (Handshake + Auth Token)
                
                alt Invalid Token
                    O-->>W: Connection Error / Disconnect
                else Valid Token
                    O-->>W: emit 'connect'
                    
                    Note over W: On 'connect'
                    W->>O: "emit 'worker:register' { workerId, specs, type }"
                    
                    O->>O: Validate Specs & Pricing
                    O->>DB: UPSERT Worker Record
                    O->>O: Add to Memory Map
                    
                    O-->>W: "emit 'registered' { success: true }"
                    W-->>W: Log Registration Confirmed
                end

Phase 2: Job Execution & Logs

The core business logic. The orchestrator pushes jobs to workers, and workers stream back logs and status updates.

            sequenceDiagram
                participant O as Orchestrator
                participant W as Worker
                participant D as Docker (on Worker)

                O->>O: Scheduler selects Worker
                O->>W: "emit 'job:new' { jobId, dockerfile, resources }"
                
                W->>W: Check availability
                W->>O: "emit 'job:status' { status: 'running' }"
                
                W->>D: Build & Run Container
                
                loop Log Streaming
                    D-->>W: "Container Log Output"
                    W->>O: "emit 'job:status' { status: 'running', logs: '...' }"
                end
                
                alt Success
                    D-->>W: Exit Code 0
                    W->>O: "emit 'job:complete' { success: true, result: output }"
                else Failure
                    D-->>W: Exit Code 1 / Error
                    W->>O: "emit 'job:complete' { success: false, error: msg }"
                end
                
                O->>O: Update Job DB / Release Worker

Phase 3: Health Monitoring (Heartbeat)

To ensure system stability, workers report their resource usage every 30 seconds. If a worker misses heartbeats for >2 minutes, it is marked offline.

            sequenceDiagram
                participant W as Worker
                participant O as Orchestrator

                loop Every 30 Seconds
                    W->>W: Collect Metrics (CPU/RAM/GPU)
                    W->>O: "emit 'worker:heartbeat' { metrics }"
                    
                    O->>O: Update LastSeen Timestamp
                    
                    opt Every 5 Minutes
                        O->>DB: Persist Heartbeat to DB
                    end
                end

                Note over O: Monitor Loop (Every 30s)
                O->>O: Check LastSeen > 2 mins?
                opt Timeout Detected
                    O->>O: Mark Worker Offline
                    O->>DB: Update Status = 'offline'
                end

4. Event Dictionary

Event Name Direction Payload Description
worker:register Worker -> Orch { workerId, type, specs, token } Initial identification after connection.
worker:heartbeat Worker -> Orch { metrics: { cpu, ram... } } Periodic health and load report.
job:new Orch -> Worker { jobId, dockerfile, resources } Instruction to execute a new job.
job:status Worker -> Orch { jobId, status, logs } Real-time updates and log streaming.
job:complete Worker -> Orch { jobId, success, result/error } Final job outcome report.
